# Visual configuration and the customer handoff

## From a product photo to a selectable configuration

The project includes real catalog door and handle references, preserved original photographs, and a visual preview so customers can explain a preferred combination. The black 8020 door and pull handle 190 shown in the public builder are an actual available UI selection; the preview is explicitly illustrative and does not certify physical fit.

Project provenance records document early image-generation experiments using a real door photograph plus catalog handle references. The requested edits removed existing hardware, reconstructed the covered surface, and placed referenced hardware while preserving the rest of the image as far as possible. Those generated mockups are approximate visual proposals, not new manufacturer photographs.

Later asset records distinguish earlier AI-prepared bases from additional original-pixel alpha masks and bounded local source cloning. The runtime renderer uses prepared door bases, original comparison images, handle layers, anchors, scale and orientation metadata to assemble an SVG preview. The inspected selector does not call an AI model on every customer selection. The portfolio therefore describes **AI-assisted visual prototyping and asset preparation**, plus a **layer-based product configuration interface**.

The implementation filters the selectable door/handle families and leaves final availability, dimensions, mechanisms and pricing to business review. It does not invent new catalog finishes or claim that every rendered pair has been mechanically certified.

## What becomes the customer case

The WordPress request snapshot records the selected door, handle, quantity, contact details, city, notes and consent. The synchronization envelope carries a combined door-and-handle item into the CRM. The work item can then show the original source and the selected configuration alongside the responsible staff member and follow-up task.

The added CRM screenshots use the actual application with independently seeded fictional records, including a combined item named “black 8020 door + pull handle 190.” They demonstrate how the interface renders this supported data contract. They do not prove that a new website submission synchronized to production during this review.

## WhatsApp is a customer-controlled handoff

The inspected WordPress formatter builds a click-to-chat URL with a request reference, selected door and handle, quantity, contact context, optional notes, source links and a statement that fit and price require review. The browser reserves an external window during the submit click, waits for confirmed website persistence, then opens WhatsApp with prepared text. The client distinguishes saved-and-synchronized, queued/retrying, and connection-check states in its status message.

The customer still presses Send in WhatsApp. Opening the draft is not evidence that a message was sent, delivered or read. This path is not an automated WhatsApp Business API integration or a provider webhook delivery system.

For the portfolio, the real WhatsApp landing page was opened with independently prepared fictional text following the inspected formatter's field order. The example deliberately omits optional image links and uses a demo reference. No website form was submitted, no live customer was created, no personal chat history was captured, and no message was sent. The complete text is included as a fictional example, not an actual customer communication.

## Evidence and boundaries

- Asset provenance records: documented image-generation pilot, approximate reconstructed bases, and later masking/source-clone methods.
- Runtime inspection: prepared-image SVG composition and door/handle family filters.
- Live browser: actual door/handle selection and original-versus-preview comparison.
- Local browser: actual CRM with a fictional combined configuration, source page and next task.
- WhatsApp browser: real prefilled landing screen; no send action or delivery verification.
